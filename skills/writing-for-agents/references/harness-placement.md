# Harness 放置合同

在新增、迁移或升格 agent harness 的规则、共享合同、脚本、Hook、checker 或 gate 前使用本合同。目标是让每项能力只存在于必要的一层，并由一个 owner 承担一种含义。

## 先证明需要存在

从已经观察到的行为或风险开始：谁在什么操作下会得到什么错误结果，不增加机制会造成什么具体后果，现有能力为什么没有覆盖。只有格式偏好、流程整齐、推测性未来需要或未经验证的风险时，不增加 harness 元素。

## 判断可迁移性

规则产生于某个项目，不等于只适用于该项目。去掉项目名称和对象后，只有同一因果机制、触发条件、判断边界、完成条件和停止条件在其他目标项目中仍然明确，且不会降低原项目的执行精度时，才泛化到可迁移的 Skill 或 reference。依赖业务语义、正式 owner、具体标签、状态、阈值、路径或运行事实的内容留在项目 owner；依赖 GitHub 等平台能力的方法可以迁移，但须保留平台边界。

通用工程方法保留在可迁移的 Skill、reference 或 script；项目规范只承接项目特有政策、经验与适配，不能为了缩短 Skill 而接收通用方法。

泛化优先改写现有唯一 owner，不复制“通用版”和“项目版”。泛化后只能给出宽泛提醒、需要额外解释才能执行，或必须新增映射层时，保留原有精确规则。

## 按能力本质放置

| 需要解决的问题 | 落点 |
|---|---|
| 需要模型理解、权衡或语义判断 | Skill 或其 reference |
| 需要跨代理、跨上下文稳定传递事实 | 共享合同；固定 owner、生产者、消费者和完成条件 |
| 输入、输出和判断稳定且可确定执行 | 脚本或 checker |
| 需要在明确的生命周期事件自动执行 | Hook；只负责触发，不拥有规则语义 |
| 违反后存在明确现实风险且可机器准确判断 | Gate |
| 属于项目业务、权限、状态、架构或运行事实 | 项目正式 owner |
| 只是格式偏好或流程整齐 | 不建立规则 |

一项能力可以跨越多层，但每层必须承担不同责任。例如 Skill 负责判断，合同负责交接事实，脚本负责收集事实，Gate 只阻断已获准机器化的风险。任何一层都不得复制另一层的规则正文或成为第二真相源。

## Gate 准入

checker 只有同时满足以下条件才升级为阻断 Gate：

- 能回链一个具体、可达的现实风险；
- 输入和判定条件稳定、客观且可确定执行；
- 受支持输入域、代表性正负样本和可接受误报上限由风险 owner 在实施前确定，实测不超过上限；已知误报不会迫使代理绕过正确工作，漏报边界已经明确；
- 失败时有清晰、有限的恢复动作；
- 执行与维护成本和被防范的风险相称；
- 不要求机器替代模型做语义、设计或任务范围裁决。

条件不全时，保留为 Skill 判断、非阻断 warning、按需诊断脚本或人工审查；不升级 Gate。

## 完成条件

一次 harness 放置完成于：拟议元素已删除，或已经具备唯一 owner、真实触发条件、明确消费者和完成条件；agent-facing 消费者通过逻辑指针到达 owner，机器消费者直接调用唯一可执行 owner；Skill 不复制项目事实，脚本不拥有语义裁决，Hook 不拥有策略，Gate 能说明风险、机器谓词和恢复动作；没有为了验证 harness 再建立一层 harness。

本合同本身不是机器 Gate，也不要求固定表单。设计与审查只需给出足以证明上述放置成立的最小理由。
