# 纵横设计

按顺序回答三件事：是否应该存在；有没有现成的做法可以直接用；剩下的部分怎样完整实现。先删除错误自由度，再证明剩下的机制；候选同等满足目标时，选可变性、负责方和补偿更少的那个。

剩下的部分分两向定，交出的是应有，实现照着做，审查拿来证伪：

- **横向定结构**：每个事实、规则、机制由谁说了算，有哪些消费者。
- **纵向定行为**：一次真实执行从触发到可观察结果，必需哪些步骤、各由谁负责、失败停在哪。

开始前读项目参数文件 [`docs/agents/review.md`](../../../docs/agents/review.md)：工作地图位置、项目探针、裁决请求格式。缺的项按本文默认。

## 1. 固定问题与深度

把输入分成**事实**（可核验的现状）、**目标**（用户必须得到的可观察结果）、**约束**（不能突破的边界及依据）、**假设**（答案不同会改变设计的未知项）。约束只有三种来源：用户或责任方的明确裁决、外部硬限制（法规、平台能力、已验证的事实）、已确认的上位目标。现有代码、历史投入、旧方案，以及现有规范和任务里的技术做法，都是上一次设计的答案，归入现状：可以沿用，不能拿来排除候选。涉及跨组织、身份、外部集成或合规时，把部署形态、外部生态和监管边界纳入输入。

按产品影响、不可逆性、失败代价和未知程度选深度，不看文件或对象数量：

- **无语义变化**（纯格式、措辞或机械同步）：输出 `无语义变化：<保持不变的负责方、行为与证据>` 后结束。
- **D1 边界裁决**：在一个既有负责方内裁决对象、规则或接缝，不改变跨模块协作、生命周期或关键质量属性；compact 地图。
- **D2 完整设计**（默认）：从触发到用户结果的对象协作、读写边界、失败恢复与验证方式；full 地图。
- **D3 架构综合**：要处理跨决策约束、部署运行、不可逆迁移、恢复回滚或长期演进；full 地图，做完下面各步后另按 [架构综合](references/architecture-synthesis.md) 展开。

工作地图：已有与当前范围绑定、形态相符的就复用，没有就调用 Skill 工具：`map-semantic-units` 生成。设计改变命题、负责方、对象、不变量、关键边或证明边界时，更新同一份地图。

正式依据冲突、没有人有权裁决，或需要用户改变产品目标时，按参数文件的裁决请求格式上报（缺省：需要决定什么、已知事实与证据缺口、建议与理由、选择后的影响），停止依赖它的工作。

**完成条件：**只有一个主要结果；每项约束写明属于哪一种来源；关键未知写明会推翻什么；深度已定；地图已固定。

## 2. 证明它该存在

1. 用户真正需要的结果是什么？只做最小一件事，用户拿不到什么？
2. 产生结果不可缺少的事实、对象和能力是哪些？
3. 所称的系统、模块或机制就是这些能力，还是历史方案的包装？
4. 不建设它，改用现有负责方、可靠默认值或更小流程，哪个真实结果会失败？
5. 能否删除自由度、收紧选择或改变对象边界，让问题本身消失？

存在与否取决于未裁决的产品目标时，停在这里：只输出存在性结论、条件分支、该由谁裁决，以及裁决前不能做的动作。

后面每冒出一个拟新增的持久对象、状态、事件、任务、投影、锁或补偿机制，回到这里用第 2、4、5 问再证一次，并加问：数据库约束、短有效期、失败关闭或更小边界为什么不够？它承担正确性，还是只改善清理速度、性能或可见性？只改善清理或性能的标为可丢失优化，不当正确性的真相源。答不出就删，不为“以后可能需要”留空槽。

**完成条件：**系统或模块能用真实结果和不可约事实证明需要存在，否则明确删除、延期或条件化；每个保留的机制有独立事实、负责方、生命周期和删除反例。

## 3. 先用现成的

需要存在的每一样东西，动手设计之前查两处，查到一处不算完：

- **外部**：所用框架、平台、库的官方推荐做法，业内成熟系统的通行做法或标准。它回答这件事应该长什么样。不是本产品独有的能力（登录、密码、会话、权限这类），必须真的去查：读官方文档，或调用 Skill 工具：`research`。
- **本仓库**：已有的负责方、模块、约定和规范。它回答现在有什么可以接着用。

答案是可核对的具体物：做法的名字和出处。外部做法的出处是文档地址或标准条目，仓库路径不算，凭印象说“业内一般这样做”也不算；查过没找到，写查了哪里、没查到，不写成“没有”。

外部的现成做法就是设计，默认照用，后面两步只设计它没有覆盖的部分。比它多出来的机制都是偏离，不论是这次想新加的，还是仓库、现有规范、任务或审查意见里已经有的。偏离要写明：照外部做法时哪个真实结果会失败，多出来的东西谁长期维护。说不出会失败的结果：新加的不加，已有的提请简化。偏离不由设计者自己定：按裁决请求格式交给技术取舍的责任方（缺省：用户）。

**完成条件：**每个要新建或改动的对象、机制和流程，都写出了外部的现成做法及文档出处，和仓库里接着用的部分；比外部做法多出来的机制逐项列出，各有一个会失败的真实结果，或已提请简化；每处偏离已交出裁决。

## 4. 横向：建立最小模型并消除错误源

从用户结果检验地图中的对象，不从页面、接口、表或现有模块反推。只有身份、生命周期、不变量、裁决权或失败行为不同才拆成独立对象。只记录设计新增或改变的事实、不变量、协作与取舍，其余沿用地图。

面对防错、恢复、补偿或对账需求，先追到产生条件：

1. 哪个重复输入、自由度、对象边界或非法状态使问题成为可能？
2. 能否从唯一负责方推导事实、删除输入、限制选择，或让非法状态无法表达？
3. 源头简化后剩下的问题属于可避免误操作、合法业务变化还是数据损坏，写入入口还要守哪些不变量？

**完成条件：**每个核心事实只有一个负责方和一条合法写入语义；每个保留对象追得到用户结果或硬约束；每项错误处理需求都说明了错误源怎样消除，或为何必须由剩余机制承接（该机制回第 2 步证明）。

## 5. 纵向：沿一次执行走到底

对每条受影响的执行链，从触发走到可观察结果，写下它应有的样子。问法用 [`zong-heng-audit`](../zong-heng-audit/SKILL.md) 的纵向六问和横向六问，这里正着答：答的是应有，不是实际。

- **能答多细就答多细。** 入口、数据访问和调用关系已经知道的，写出次数表达式、计数单位和持有范围；还不知道的，写形状——工作量随什么增长、哪一步不该随它重复、失败停在哪——并注明留给实现前那次设计补全。
- **要下游遵守的答案是承诺。** 写进工作地图的不变量，并在 Proof / oracle 里配上会失败的强制手段：约束、类型、测试、门禁或告警。配不出强制手段的只是设计说明，留在产出里，不进地图。

承诺的样子：“授权判定每次请求求一次，不随行数重复”；“总数按人计，不按关系行计”；“这个口径由名单的负责方定，其余出口只引用”；“外部调用不在持锁的事务里”；“回写失败停在可查的待处理，由指定的人接手”。

**完成条件：**每条链的必需步骤各有负责方；随数据放大的、不可逆的、多个入口共享的步骤已答到次数或形状；每条承诺有强制手段，或已标为设计说明。

## 6. 有分歧才比较，成形后才攻击

- **候选**：只在有两个以上真实可行方向时生成完整候选。它们共享同一问题、约束和不变量，由不同优化目标驱动，各自独立闭合对象、负责方、写路径、执行链和失败恢复，写明牺牲与推翻证据；违反硬约束的只记为排除路径。用核心、质量和失败场景逐个施压，推荐方案赢在场景和证据，淘汰的写明输在哪个场景。只有一个合法方向时写明它和排除依据，不制造伪分歧。需要调用 Skill 工具：`prototype` 时，先定问题、判定阈值和停止条件。
- **探针**：模型和执行链的第一版形成后，D2、D3，或命中动态候选集、失败恢复、版本替换、跨负责方交接、临时资源、部署证据或验证机制时，读 [失败反例](references/gotchas.md) 和参数文件给出的项目探针，攻击已形成的设计。命中后回到用户结果重新裁决：能删错误源就删，确需新机制回第 2 步证明。

## 7. 输出并停止

- 各档都交：结论、用户结果和最大风险；深度、设计与不设计的边界；现成做法里照用了什么、偏离了什么及理由；当前工作地图（含新立的承诺及其强制手段）和对象模型的设计增量；正式回写位置和未决裁决。
- D2、D3 必交，D1 命中才交：事实、约束、假设和证据缺口；真实候选、排除路径和裁决理由；执行链的应有、失败恢复与验证方式。
- D3 再交架构综合材料。

交付要让实施者不必重新发明核心语义，让验证者知道怎样证伪关键主张。没有实现、测试或运行证据时只报告待验证。推荐方案需要用户裁决而尚未取得时，停止并输出未决裁决。
