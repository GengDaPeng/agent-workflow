# PR 评论协议

`[REVIEW]`、`[FIX-REPLY]`、`[RECHECK]` 的格式只在这里定义。本地返回与 PR 发布用同一份草稿。首行写参数文件给出的身份前缀加真实模型 ID，例如 `评论者：<项目>-<模型ID>`。

## 发现项

- 有候选发现或范围争议时，本轮集中调用一次 Skill 工具：`task-closure`，读其 `finding-disposition` reference。
- 只有存在现有证据没覆盖的、不同且可达的真实风险，才因缺测试或缺证据建 RR。为“证明的证明”补测试不阻断。
- 每条发现分别标严重程度和证据等级：

| 证据等级 | 成立条件 | 必须给出 |
|---|---|---|
| 规范已定 | 正式规范明文与被审对象矛盾 | 原文摘录、文档和章节 |
| 代码自相矛盾 | 同一仓库对同类问题有冲突实现或表述 | 两处 `path:line` |
| 实测证实 | 运行或测试证明结论 | 原始结果和复现条件 |
| 推论待裁决 | 没有明文，结论来自阅读推断 | 检索范围、未知点和待裁决表述 |

说“违反规范”却给不出原文，或说“规范没规定”却没检索，一律降为推论待裁决；推论待裁决不进 MUST。

## REVIEW

`MUST` 表示至少一条 RR 须在本次交付闭环；`PASS` 表示没有活动发现。建议可写进正文，但不是机器状态。

```md
评论者：<项目>-<模型ID>
[REVIEW][MUST|PASS]
结论：通过 / 仍需修改

## 必须闭环
无。或 RR-xxx：问题、依据、可达场景、影响、最小动作与初步处置

## 复核元数据
- 任务分级：B级 / A级 / S级
- 审查版本：<当前 PR head 的 40 位 SHA>
- Context 版本：<仅 discussion 来源保留>
```

证据不足以可靠分类时，只返回“审查未完成”、已覆盖范围、缺口和恢复条件，不出结构化状态。需要用户裁决的成立问题用 `MUST` + RR 返回裁决包，并停止依赖它的工作。`MUST` 发布后返回修复交接包，不再读取正在变化的实现。

## FIX-REPLY

开发方一轮处理完，按修复 head 发一条汇总；一条可承接多个来源和 RR：

```md
评论者：<项目>-<模型ID>
[FIX-REPLY]
来源：<REVIEW URL 或评论 id> [RR-001][RR-002]
修复版本：<40 位 SHA>
处理：每个 RR 的落地结论
证据：直接命中结论的证据
```

用户裁决本身不关闭 RR：FIX-REPLY 写明裁决如何落地，再由审查方复核。修复未推送、head 漂移或来源失效时，只返回未发布草稿。

## RECHECK

审查来源 REVIEW 版本到 current head 的完整增量。增量里的新问题在 `[RECHECK][MUST]` 中分配新 RR，继续引用原 REVIEW，不另发 REVIEW：

```md
评论者：<项目>-<模型ID>
[RECHECK][PASS|MUST][RR-001][RR-002]
来源：<原 REVIEW URL 或评论 id>
复核版本：<当前 PR head 的 40 位 SHA>
任务分级：B级 / A级 / S级
Context 版本：<仅需要时保留>
结论：通过 / 仍需修改
证据：复核依据
```

`PASS` 只在所列 RR 已闭环、完整增量没有其他活动发现时使用，它同时关闭这些 RR，并作为该 head 的复核结论。

## 发布与回读

- 发布前重读 live PR head，等于审查版本才发布；变了不发旧草稿。用 `--body-file` 发布，返回 PR、版本、评论 URL 和结论。
- 成文后用参数文件的评论校验命令核对身份、分级、版本与结论字段；发布后把单条评论的 API JSON 存成文件做回读校验。原位修改用原评论的 REST `id`，不用 GraphQL 的 `databaseId`。
- 校验通过只说明字段一致，不说明语义审查通过或 RR 已闭环。

## 等待对方评论

开工指令启用了 `agent-message` 时，按它直接交接，不用脚本。未启用时用脚本等对方新评论；同一 PR 同一角色只保留一个监听进程：

```bash
node <skill-dir>/scripts/wait-pr-comment.js --pr <编号> --role <reviewer|developer> --after-comment <起点评论 ID> [--once]
```

- 审查方发布后用 `reviewer`（等 FIX-REPLY）；开发方开 PR 或发 FIX-REPLY 后用 `developer`（等 REVIEW / RECHECK）。
- 宿主能在同一回合持续读取进程输出时（如 Codex 的 `exec_command` + `write_stdin`，或 Claude Code 的 Monitor），用持续模式。否则加 `--once`，后台启动，结束回合时报告 PR 链接和在等哪一方，由完成通知恢复；处理完这一批后，以其中最大的评论 ID 作起点重启。
- 输出只有 `{id,type,url}`，按 id 读原文后走原流程。`PASS` 不结束监听；PR 合并或关闭时脚本以 0 退出。
