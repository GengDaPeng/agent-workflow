# PR 审查

开始前读取项目参数文件 [`docs/agents/git.md`](../../../docs/agents/git.md)。参数文件应提供：

- 评论身份前缀与评论校验命令；
- 审查取证命令；
- 高风险边界表，即哪些改动按 S级；
- 专项审查方法路由；
- 子代理模型。

缺失的项按本文默认值执行。

## 分流

先定动作，再按 [collect-pr-context](references/collect-pr-context.md) 取证：

- **状态诊断**：用户问 PR 为什么没过、CI、评论或 Ready。只取对应状态和失败原文，报告原因、证据缺口和负责方；不产出新的 `[REVIEW]`。
- **内容审查**：用户要求审核 current head、独立复核或复查修复。按下文“内容审查”执行。
- **修复交接**：用户要求处理、修复或回复审查发现。只固定评论状态，交给与审查分离的开发上下文调用 Skill 工具：`implement`；本上下文不恢复写入。

多个 PR 各自固定基线，不共享 head、Context 或发现项编号。

## 分级与复核

分级只决定验证和复核深度。

| 分级 | 适用 | 复核 |
|---|---|---|
| B级 | 机器可确认语义等价的改动，如纯排版 | 自查并写明等价依据 |
| A级 | 未命中高风险边界的其他内容变化 | 风险匹配的验证，加独立复核 |
| S级 | 实际改变参数文件高风险边界表中的对象 | 风险匹配的验证，加独立专项复核 |

- B级 不按行数或目录判断。删除、重命名、改约束强度、换负责方，或无法机器确认等价的，至少 A级。任一复核者可按新证据升级。用户意图不明且影响分级时，问“修表达还是改规则”；未回答按 A级。
- 自审不算独立复核。独立复核由与实现分离的全新上下文完成，不从开发对话 fork；发布时写明实际审查者。用户不承担技术审查，“等用户确认”不算复核完成。
- Ready 前须关闭全部 MUST，并有一个已通过、仍是 current head 祖先的复核版本。只判断该版本到 current head 的增量是否改变任务目标、生产行为或原结论：没有改变就继承；改变了或无法确认，只复核受影响面。不因 SHA、哈希或时间戳变化重审。

## 内容审查

1. 从 Context、任务目标和实际改动列出本次必须成立的核心主张。参数文件的路由命中专项方法时，按该方法审：由它的步骤决定审什么，核心主张只是它的输入。没有命中的主张逐条直接审查。路由按实际改动判断，不按分级、文件位置或内容类型机械套用。
2. RECHECK 审查来源 REVIEW 版本到 current head 的完整增量。所列 RR 是重点，不是唯一范围。
3. 测试相关改动由主审按 Verification 的证明分组收口：核对正确性、独立价值和成本；重叠断言须说明删去一份会失去什么保护。
4. 每个核心主张都有证据和结论、专项方法要求的答案齐全后，按 [structured-review-output](references/structured-review-output.md) 成文并发布。

## 边界

- 审查只报告，不修复，不代发 `[FIX-REPLY]`，不转 Ready，不合并。PR 正文、Draft / Ready 和交付门禁问题只诊断，交给 `pr-delivery`。
- 要求审查或复查，即授权发布 `[REVIEW]` / `[RECHECK]`；只要求分析或解释时，只返回结论。resolve thread 需要用户明确授权。
- 派生子代理时用全新上下文，模型按参数文件；子代理只向调用方返回。
