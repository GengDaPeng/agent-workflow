# 纵横审查

审查者是改动的对手方。diff、PR 描述和作者解释都是待证伪的主张；“通过”是证伪失败后剩下的结论，不是默认值。

结果正确不等于改动成立。要审的是系统实际做了什么、实际长成什么样，与它应有的差在哪：

- **纵向审行为**：沿一次真实执行，从触发走到可观察结果，把系统实际做的每一步摊开，与达成这个结果所必需的步骤对照。
- **横向审结构**：把同一个事实、规则或机制的全部出现处摆开，与“只有一处说了算”对照。

差只有三种：**多了**（没人用的产出、重复的判断、没退役的旧物）、**少了**（没有收场的失败、漏掉的消费者、没人强制的承诺）、**不一样**（与同类做法不同、与声称的不同）。

本方法不审改动是否符合成文的编码规范、是否实现了需求条目，那由 `two-axis-code-review` 审；走哪个或两个都走，由上游审查者按项目参数路由。开始前读项目参数文件 [`docs/agents/review.md`](../../../docs/agents/review.md)：工作地图位置、项目探针、L3 触发条件、旅程来源、页面依据与走查账号、子代理模型、裁决请求格式。缺的项按本文默认。

## 1. 固定对象与依据

- 固定审查对象、基准版本和不审范围。对象是 PR 时，由 `pr-review` 固定 current head 与原始证据，这里直接用。
- 原始证据是改动全文或 diff、任务或用户指令、命中的正式规范、测试与运行证据，缺什么标什么。PR 正文、对话结论、记忆和门禁通过只是待核材料。
- 找到 `map-semantic-units` 的工作地图，确认它在不在、全不全；内容留到第 2 步写完应有之后再用。它是作者交出的那份应有，用来对照命题与边界、找位置，不用来抄答案。缺失时到参数文件给出的位置恢复（缺省：任务临时文件，再到 PR 正文的 `[SEMANTIC-MAP]`），恢复不了的部分记为缺口。
- 选强度。**L2**（默认）：一个上下文分纵、横两遍。**L1**：只涉及一个边界清楚的对象，不改负责方、生命周期、不变量或失败边界时，只审这个对象；发现要拆对象就升 L2。**L3**：触及核心业务链路、访问控制、生产数据、不可逆迁移或参数文件的触发条件时优先，一个上下文装不下时必须；两向交给独立分组，按 [分工与回收](references/multi-agent-boundary.md)。增量复核按本轮要重判的范围选强度，报告写明原强度与继承了什么，不冒充重做了 L3。

## 2. 先写应有，再读实际

读实现和地图之前，从任务与正式依据写下应有的样子。纵向：这次执行必需哪些步骤、各发生几次、失败时该停在哪。横向：这件事该由谁说了算、有哪些消费者、同类是怎么做的。然后读实现，逐问对照；再打开地图对照。只读实现或地图再点头，等于让作者替你定了答案。取证时已经看过地图或实现的，应有仍只从任务与正式依据推，并在报告里写明。

你的应有与实现不同，是发现。与地图不同，是地图有问题：按 `map-semantic-units` 返回 `MAP-CHALLENGE`，不另建平行地图；它不算发现项，但证据充分的风险不等地图修订，立即成为发现。

每一问的答案是可核对的具体物：一处代码位置、一个名字、一个次数表达式、一次真实运行的输出。“已检查”“未发现问题”不是答案。某一问在这里不成立，写出使它不成立的事实和位置；答不出，记为缺口并写明缺什么，不并入通过。

不可逆的、多个入口共享的、随数据放大的、与同类做法不同的步骤，逐问全答；其余步骤答纵向前两问。

## 3. 纵向：一次执行的每一步

一条执行链是一条业务命题：谁或什么触发、在什么前置状态下、系统必须形成什么可观察结果。只沿真实存在的链路走，不用模拟、临时回调或未来设计补成闭环。

1. **必要**：这一步的产出被谁用掉？没人用，或只用掉一部分，是多做。
2. **数量**：这一步发生几次、处理多少、数的是什么单位（每次请求还是每行，按人还是按关系行）？写成表达式，指出乘数来自哪个集合、真实规模多大、上界在哪。
3. **持有**：它在哪个事务、锁、连接或会话里进行，从哪一步取得、到哪一步释放，期间在等谁？范围和强度与这一步的读写性质相称吗？
4. **归责**：链上每个判断（权限、校验、不变量、统计口径）由哪一步负责？别处出现的同一判断，是重复、假设，还是另一套判据？
5. **断点**：在这一步之前、之中、之后被中断、重复或并发执行，事实停在哪、谁能发现、怎么回到合法状态？
6. **实证**（每条链答一次）：结论由哪一次真实运行证明？它的入口、数据、版本和装配与正式链路相同吗？读代码只证明形状，量级要有测量；没有测量写“形状已核，量级未证”。

## 4. 横向：一件事的每一处

出现处只列真实存在的和正式裁决过的，不推测未来；包括未改的文件，以及任务和地图没点名的。

1. **唯一**：谁说了算？其余出现处是引用还是副本，副本靠什么保持一致？
2. **穷尽**：改动触及的合同有哪些消费者？逐个列出，不抽样，标明仍成立、已修改或有缺口。
3. **对照**：同类（同类入口、列表、写命令、检查）怎么做同一件事？这里不同，要么有记录在案的理由，要么是发现；没有同类就对照业内通行做法。
4. **兑现**：改动引用或新立的每条承诺（规范、裁决、预算、PR 声称、注释里的保证），由什么会失败的东西强制——约束、类型、测试、门禁还是告警？指不出，它只是文字。
5. **新旧**：新机制生效后，旧入口、旧任务、旧凭据、旧常量还能运行吗？新机制是否与某个已有机制做同一件事？
6. **绕行**：绕开共享包装或公共路径时，那层包装原本附带哪些条件，新路径逐条怎么保住？

## 5. 交叉与探针

- 纵向的每个裁决点和写入点，是否落在横向确认的负责方上？有没有绕过它的入口？
- 横向列出的每个消费者和能力，是否被至少一条真实执行用到？
- 执行结果正确时，外围的契约、投影、证据或旧入口是否还在表达另一套说法？
- 纵向的次数表达式乘以横向的调用入口数，才是这一步对全系统的工作量；共享步骤按乘积判断。
- 两向对归属、状态含义或完成证据的结论冲突时，单独记为交叉发现；一向通过不覆盖另一向的阻断。

两向答完后才加载探针，用来攻击已有结论：[失败反例](references/gotchas.md)，以及参数文件给出的项目探针。

设计稿，或改变用户可见页面、流程、反馈、可见性的改动，另读 [页面取证](references/ui-review.md)，**用真实浏览器走查**，证据并入同一份答案。

## 6. 输出

审查只报告，不修复。报告写：

- 对象、版本、强度和证据状态；总体结论与最大的失败风险。
- 每条执行链、每件事各一段：先是读实现前写下的应有，再是各问的答案、不成立的事实或缺口。与应有不同的地方，标出对应的发现，或写明它为什么不是发现。
- 发现项。严重程度、证据等级与 RR 按 `pr-review` 的 `structured-review-output`，处置按 `task-closure` 的 `finding-disposition`；成立的问题即使处置是另行跟踪，也分配 RR，结果返回前不判通过。每条另写问出它的视角和所属根因组：同根的发现归一组，修复与复核按组进行，组内还有未处置的当前命中就不关闭。
- 未实现的片段：属于当前任务验收范围的是缺陷；已正式推迟且有负责方和承接任务的，写成不证明边界；两者都不是，记为结构性缺口。

发现与答案一并交回 `pr-review` 成文发布，答案的位置按它的评论协议。写验证探针用 `tdd` 的 `test-design`，运行或复用验证证据用它的 `verification-execution`。需要用户裁决时按参数文件的裁决请求格式（缺省：需要决定什么、已知事实与证据缺口、建议与理由、选择后的影响）。阻断或严重的发现，注明是否值得按 [失败反例](references/gotchas.md) 的规则回补。
