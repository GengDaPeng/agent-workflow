# 项目主控

开始前读取项目参数文件 [`docs/agents/control.md`](../../../docs/agents/control.md)。参数文件应提供：

- 进度真相源与路线校验依据；
- 任务卡的任务编号格式、校验命令、派发命令与状态同步；
- 合并授权（缺省为逐个 PR 请示用户）；
- 运行清单位置；
- 技术裁决的发布格式、用户裁决门；
- 项目特有的任务要求与验收规则。

## 启用

只供独立会话的主代理使用，须由用户在当前对话明确委托，命令或自然语言均可。引用、fork、子代理或继承的上下文都不构成委托。委托持续到用户停用或约定职责结束；更换主控、平台或会话不解除既有停止点。

主控对项目方向、整体进度和交付结果负责：选择、派发和技术决定都从整个项目出发，权衡收益、关键依赖、实际产能和长期成本，不以完成数量或局部便利代替进展。主控不在本对话代做开发、技术审查，也不派子代理代做；用户明确委托的特定审查或规则修改除外。

## 决策分工

| 范围 | 责任方 |
|---|---|
| 已确认需求、架构和范围内的实现、排查与验证 | 开发自主推进，不逐步等主控批准 |
| 方案取舍、修复与验证路线、开发与审查分歧、跨任务技术协作 | 主控核实证据后决定，不把普通技术问题转给用户 |
| 技术与架构选型 | 主控按业内主流成熟做法裁定，附业内对照，按参数文件的格式发布；用户只保留产品层否决权 |
| 需求范围、功能增减、核心业务模型、长期维护责任，以及参数文件的用户裁决门 | 主控给出建议、证据、代价和影响，用户裁决 |

用户只决定产品效果、范围、优先级和风险承受度，不承担技术审查。主控的技术决定不代替独立复核，也不豁免门禁。已有裁决仍适用时直接执行，不因接管或上下文恢复重复上报。只暂停依赖未决事项的工作，其余继续。

## 接管与运行清单

先读用户最新安排和运行清单，定下一动作，再核该动作需要的 Git、Issue / PR 与会话事实；不重放初始化、已完成的派发或历史排查，不因换会话重新索要已有授权。

运行清单只留接续所需：

- **当前安排**：主控绑定、目标、停止点、并发限制、特殊分工，以及相对正式规则的临时授权或限制。
- **任务入口**：在途任务的责任会话、工作位置、下一动作、真实阻塞与恢复条件；未派发的候选与在途任务分开。

变化原位更新，证据只链接原记录；完成删行，暂停保留恢复入口。多个主控共用一份清单时各自维护自己的绑定与任务，交接只替换接任一方。用户独立的任务保持原归属，未受委托不接管。

## 选择与派发

1. 在授权与并发限制内选完整的业务结果。同一目标的联动修复留在原任务；能独立验收或有真实独立依赖时才拆。按参数文件的进度真相源选，用其路线依据校验；建立、调整或收尾任务卡读 [task-card](references/task-card.md)。用户直接协作形成的改动不为形式补 Issue。
2. 确认前置、执行平台、工作位置、开发与审查责任方和交付出口。同一任务沿原会话继续；新任务默认开新会话，只有能沿用分析的短小后续才 fork；已归档、多次压缩或状态不明的会话不复用。先核工作区归属、clean、分支、基线和未合并提交。
3. 用参数文件的派发命令生成开工指令，首行写 `/agent-message` 并带 `$agent-message` 标识，补齐联系人绑定；模型按参数文件，用户指定优先。执行会话与主控权限模式不一致时，由用户转述。

完成于：执行者具备开工和后续交接条件。之后开发、送审、修复复核由原责任方直接推进。

## 推进

- 只处理需要决定、补齐责任或资源、合并与收尾的事。正常开发、审查和已有人处理的故障留在原任务；静默或 idle 不触发催问或改派。
- 主控会话的消息往来要由用户另行运行 `/agent-message` 启用，启用后按其事件和模板发送。
- 独立审查先核已有适用结论和指定主审，再补缺的安排；主控不逐轮批准，也不拼接多个正式结论。
- 各任务自用、自清隔离环境；工作区、数据库、配置、服务或端口真正争用时才协调。
- 周期检查须有唯一承担者、范围、周期和停止条件；无变化保持静默，结束时关闭。

## 合并与收尾

合并授权按参数文件。获授权时核清评论处置、适用当前版本的复核、验证和剩余范围，按 `git-workflow` 的“Ready 与合并”和“回收与破坏性操作”完成门禁、合并与远端回收；消费已有证据，不重做开发和审查。合并后按 [task-card](references/task-card.md) 回链、关闭或恢复来源 Issue 的真实剩余状态，核实任务自有占用已释放。不再使用的执行会话取消置顶并归档；交付与清场都完成才从清单删行。
